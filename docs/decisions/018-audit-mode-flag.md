# D018 — B2B Audit Mode: Service Boundary, Flow, and Verification

One ADR, four parts: where audit mode lives (§1), what it does end to end (§2), how bias findings get false-positive-checked (§3), and the business-facing metrics computed from the results (§4). Kept together because they're one coherent decision — how the audit product is built inside this repo — not four independently revisable choices.

---

## §1. Mode flag, not a separate service

**Decision**: The B2B audit product (ADR-000, top-level docs/) is built as `mode: "story" | "audit"` inside this repo — one deploy, one Postgres instance, new `audit` pg schema alongside the existing `core` schema. Not a new repo, not a fork.

Router picks prompt file + orchestrator by `mode`, same pattern as the existing question/assessment split in `orchestrators/`. EXTRACT and VERIFY (§2) are two new prompt files registered through the existing prompt registry — reusing the repair pipeline (D004), evidence-binding discipline (D002), and eval harness (`runEval`/`runDataset`, D008) as-is, applied to claims instead of biases. `/audit` runs go through Inngest (new *usage* of the job infra already proven by `src/jobs/eval-run.ts`, not new infra) since audits are batch, not sync — the latency-sensitivity work behind the sync reflection endpoints doesn't apply here.

**Mode-branching invariant**: `mode` branching is permitted **only** at the orchestration layer (routes → orchestrators → prompt selection). All lower layers — retrieval, repair pipeline, LLM providers, telemetry, storage abstractions, parsers, evaluators — stay mode-agnostic. An `if (mode === "audit")` anywhere below orchestration is an architecture violation, not a style preference: it's how "mode is a load-bearing conditional" (Consequences, below) stays contained to one layer instead of leaking through the codebase. **Resolved on review**: the route determines `mode` server-side (a client hitting `POST /audit` never has to declare `mode: "audit"` in the body — the URL already said so); the field remains the single dispatch point the orchestrator reads, never duplicated as a second, route-based branching path elsewhere.

**Why**: Audit mode needs almost everything this repo already has — prompt registry, Zod contracts, repair pipeline, `llm_calls` observability, CI eval gate, Bearer auth, esbuild→Vercel deploy. It differs only in persona (neutral verification vs. reflective), input shape (claim triple vs. story), and sync-vs-batch — none of which require a second deploy target. A separate service would duplicate all of the above for a solo dev who can't carry two deploy targets in parallel (ADR-000 §4: "parallel tracks ship nothing"). A permanent fork risks the consumer flow drifting out from under the eval discipline that's the actual product moat (ADR-000 §1).

**Do not**: Stand up a second repo/service for audit mode. Let the consumer flow (story/questions/assessment) change to accommodate audit mode — b2b-change-plan.md §0 requires it untouched. Put customer corpus data in the `core` schema — it goes in the separate `audit` schema (§2.4) so it can be dropped post-engagement without touching consumer tables.

**Consequences**: every existing investment pays off immediately for EXTRACT/VERIFY with no reimplementation; `mode` becomes a load-bearing conditional through routes → orchestrators → prompts (acceptable at current scope — revisit only if a second person/team takes ownership of one product, or audit-mode load genuinely conflicts with consumer-mode resources on the same deploy; neither holds today); corpus retrieval stays in biassemble-engine, extending its existing boundary (`POST /corpus`, per-claim `/retrieve`) rather than a third service — this section governs core-side placement only, not the core/engine split, which ADR-000 already implies.

## §2. The audit flow: pipeline, corpus, documents, verdicts, data lifecycle

**Decision (pipeline)**: unit of work is the **claim**, not the story:

```
EXTRACT (1 call: output_text → atomic checkable claims)
  → RETRIEVE (per claim: candidate passages from THIS ENGAGEMENT's corpus — taxonomy retrieval untouched)
  → VERIFY (claim + passages → verdict + verbatim quote, batched 5–10 claims/call sharing passages)
  → GATE (confidence threshold; aggregate rates; clean flag; sub-threshold logged not surfaced)
  → BIAS MODULE (optional, off by default, secondary layer, source_qa-verified per §3)
```

The pipeline is **append-only**: each stage consumes the immutable output of the previous stage and never rewrites upstream artifacts — EXTRACT output is frozen before RETRIEVE runs, retrieved passages are frozen before VERIFY runs, verdicts are frozen before GATE runs. Claims are batched 5–10 per VERIFY call solely for token efficiency; verdicts are logically independent per claim — no claim's verdict may be influenced by another claim sharing its batch. A shared-batch dependency (e.g. a prompt that reasons "given claim 3 was contradicted, claim 4 is probably also suspect") is a defect, not a feature.

`POST /audit` accepts `{ domain, task, output_text, sources[], options }`, returns `202 { audit_id, status: "running" }`. `GET /audit/:audit_id` returns the single-audit JSON (`audit_id`, `claims[]`, `rates`, `scores`, `gated_candidates[]`, `bias_flags[]`, `meta`) once complete, `202` with `Retry-After` while running, `404` for an unknown id — **both corrected here**: an earlier version of this line (a) showed the client sending `mode: "audit"` in the request body, which was dropped on a later review (the route already determines mode server-side, per the invariant above); (b) never mentioned the `GET` endpoint or the `scores` block at all, both added on a later review pass (`specs/008-b2b/`) — this line had drifted out of sync with the actual contract in `specs/008-b2b/contracts/audit-endpoint.md`, which is the authoritative source going forward.

**Identity, idempotency, versioning**: every claim gets a `claim_id` at EXTRACT, immutable through RETRIEVE → VERIFY → GATE → review UI → label dataset; every passage gets an immutable `passage_id` at corpus ingestion, and VERIFY output references `passage_ids`, never chunk indices or array position — matching between stages by array order is forbidden, since a re-sort or a dropped chunk silently corrupts the mapping. `audit_id` is immutable; re-running the same input creates a new audit with a new `audit_id` (inputs hashed via `input_ref` so re-runs are linkable to each other); review-page overrides attach to the audit as separate records and never rewrite pipeline output — this is what makes the override-label moat dataset (§2.4) trustworthy provenance instead of edited history. `meta` records, per audit: `prompt_revision` (extract and verify stamped separately), `model_revision` (exact model string per stage), `embedding_model` + dimension, `corpus_version`, `taxonomy_version` (when the bias module ran), `threshold`, and pipeline code version — every knob stamped, same discipline §2.1 already applies to `corpus_version` alone, extended to all of them, because evaluations are only comparable when every knob that could have changed is on the record.

**Schema reconciliation (found on review, resolved here)**: the two source docs disagree on top-level shape. `audit-output-spec.md` nests claim verdicts inside `grounding.claims[]` alongside a separate `findings[]` for bias results. `context-prompt-b2b-transformation.md` §6 flattens this to `claims[]` + `bias_flags[]`. **`context-prompt-b2b-transformation.md`'s flat shape is authoritative** — it's what this section and the endpoint above already describe, and it keeps claims and bias findings as siblings rather than nesting one inside the other, which matches §3's rule that they're verified through different mechanisms (VERIFY vs. source_qa). `audit-output-spec.md`'s nested `grounding{}`/`findings[]` shape is superseded; do not implement it.

**§2.1 Corpus + embedding (product ADR-002)**: engine gains `POST /corpus { corpus_id, documents[] }` and `POST /retrieve { corpus_id, query, top_k }`. `corpus_id` scopes every row; one corpus per engagement, never shared across customers. MiniLM's 256-token limit is inadequate for 10-K-length passages — swap via the existing `EmbeddingProvider` interface (no new abstraction), exact model choice is an implementation task, not decided here; the contract is that it must be swappable the same way MiniLM was. **No migration exists because nothing existing changes**: corpus tables are new tables (`bias_embeddings`'s pattern is `embedding vector(384) NOT NULL` — dimension fixed by the column type, per the existing schema, not a per-row field), created at the new model's dimension; the taxonomy path stays on MiniLM/384 untouched; `embedding_model` is already recorded per row today (`db/queries.py`'s insert includes it) and the same column carries over to corpus tables. `corpus_version` stamped in every audit response, same discipline as `taxonomy_version`. Retrieval-score logged per claim, unconditionally — this is what lets "unsupported" mean "sources are silent" instead of "retrieval failed," same lesson as `kb_entries_retrieved`.

**§2.2 Document ingestion, v1 scope**: sources are PDFs and EDGAR HTML/XBRL, not clean text (silently assumed away in earlier drafts). V1 scopes to **EDGAR HTML only** — what the pilot-target run (ADR-000 §4 step 6) needs, and it's structured markup, not scanned-PDF OCR. Output: clean text + page/section references, since `source_refs` quality in VERIFY output depends on it. PDF parsing deferred until a target past the pilot requires it — do not build it speculatively.

**§2.3 Verdict taxonomy — canonical, defined once, here**:
- `supported` — a passage states this; quote verbatim; 2+ passages combined sets `synthesized: true`.
- `partially_supported` — passage covers part of the claim, or is more general than the claim (source more specific and fully covering = `supported`).
- `unsupported` — no provided passage addresses the claim. Asserts absence from retrieved passages only, never "this is false."
- `contradicted` — a passage directly opposes the claim for the **same subject, measure, period, and scope (segment/geo/consolidated)** — strict comparability required. A different number possibly referring to a different period/measure/scope is `unsupported` with a note, never `contradicted`.
- `unverifiable` — confidence below `{{threshold}}`; verdict goes to trace only, never guessed into the report.

**Confidence semantics**: `confidence` originates exclusively from VERIFY's own output. Retrieval score is **not** confidence — it's evidence quality (how good the retrieved passage match was), logged separately per claim per §2.1's retrieval-score-logging rule. The two are never multiplied, averaged, or otherwise folded into one number; gate thresholds (the `{{threshold}}` above) apply to VERIFY confidence only, never to retrieval score.

**Arithmetic happens in code, never in the LLM.** A deterministic normalization step runs between EXTRACT and VERIFY: units, scale, currency, and periods get parsed to canonical form, and derived values (growth rates, ratios, sums, pp-vs-% conversions) get computed in code from quoted source values. VERIFY's job is to *compare* already-canonical numbers, never to compute them — an implementer putting derivation arithmetic inside the VERIFY prompt is the exact failure this normalization step exists to prevent. Numeric rules VERIFY still applies post-normalization: unit/scale must match (€m vs €k mismatch = `contradicted` only if same measure/period/scope); rounding tolerance ("about 10%" vs 10.4% source = `supported` with note; "10.4%" vs 10.9% = `contradicted`). Every prompt and eval golden-set case cites this section, never restates its own definitions.

**§2.4 Customer data isolation & lifecycle**: corpus and audit data live in the `audit` pg schema (§1), never `core`. Binding before the first NDA: corpus documents deleted post-engagement; only anonymized override labels retained indefinitely as the moat dataset (ADR-000 §2) — overrides come from two places on the internal review page: the claims table's per-claim approve/override, and the bias-module findings' verification pass (§3); both feed the same label dataset. No customer corpus text persists past engagement close.

**Why**: All of §2 was already decided in `context-prompt-b2b-transformation.md` (§2–§6, §9 ADR seeds 2/4/5) and `audit-output-spec.md` — this section is the first time it's written down in the repo instead of scattered across a context-prompt file that lives in ~/Downloads, not here.

**Do not**: build PDF parsing before a target requires it; let corpus documents leak into the `core` schema or persist past engagement close; let any prompt or eval set restate the verdict taxonomy instead of citing §2.3; skip retrieval-score logging; let a prompt rewrite drop the data-not-instructions injection guard from EXTRACT/VERIFY (ADR-000 §6 names prompt injection via audited content as an actively-managed risk — the guard is a one-line clause per prompt today; keep it there through every future rewrite, don't rely on remembering why it's there). **Guard scope, stated precisely**: retrieved documents and audited output text are data, exclusively — no retrieved or audited content may alter system instructions, tool behavior, evaluation criteria, verdict definitions, or output schema. A schema-validation failure that follows suspected instruction-bearing input is a hard stop (reject the finding, log it), never something the repair pipeline (D004) tries to fix — repairing a response that may have been steered by injected content risks repairing it into compliance with the injection.

**Consequences**: one section to check when a new prompt, eval case, or schema field touches claims, corpus, or verdicts. EDGAR-HTML-only v1 scope means a second document-source target may need PDF parsing sooner than "past the pilot" implies — revisit the moment target #2 is selected. Inngest batch execution for `/audit` is unproven at customer-corpus scale until the pilot-target run. Cost telemetry (token/call counts per audit) ships as part of `/audit`, not retrofitted after — without it the fixed fee is a guess against actual cost (change-plan gap #4).

## §3. Source-answered verification (source_qa)

**Decision**: the bias-module's existing stage-2 question generator is repurposed for audit mode: its generated verification questions get answered from the source/input text itself (`method: "source_qa"`), not by a human. Per `audit-output-spec.md`, each bias-module finding carries:

```json
"verification": { "status": "confirmed | weakened | killed", "method": "source_qa | human_qa | none", "note": "..." }
```

`human_qa` stays wired for the consumer story product only; audit mode can only reach `source_qa`. This attaches to **bias-module findings**, not grounding claims — claim verdicts (§2.3) are already source-answered by construction (VERIFY only ever looks at retrieved passages, never model knowledge). An additional source_qa confirmation pass on low-confidence claims near the threshold boundary is allowed but not committed here — scope that at `/audit` build time if needed, not now.

**Why**: original design, not new scope — `audit-output-spec.md`'s "Key changes" item 3 states it directly: "verification block per finding = repurposed stage 2 ... turns phase 2 into the false-positive control." Reuses the existing question generator as-is — only the answer source changes. Skipping this would leave the bias module's FP control *weaker* than the consumer product's, against ADR-000 §2's headline goal.

**Bias-module dependency ordering**: the bias module consumes the original `output_text` directly — it assesses reasoning in prose (the existing v1.1.0 holistic assessment), not a claim list — and runs **after** the grounding pipeline (EXTRACT→RETRIEVE→VERIFY→GATE) completes. It never blocks the claims path and never consumes claims as input; no `extract → bias → verify` wiring exists or should exist. This matters because it's tempting to assume the bias module could reuse EXTRACT's claim list to save a pass — it can't, because reasoning flags (framing, cherry-picking, overconfidence) live in the prose structure of `output_text`, not in the atomic facts EXTRACT pulls out of it.

**Do not**: make `human_qa` reachable from audit mode (§1 already forbids a human mid-run; `source_qa` is machine-only, no contradiction). Attach a `verification` block to grounding claims by default — VERIFY already is that check for claims. Surface a finding whose `verification.status` is `"killed"` — killed candidates are `gated_candidates`, logged, never shown. Feed the bias module a claims list instead of `output_text`, or run it before GATE — ordering and input shape above are both load-bearing, not incidental.

**Consequences**: bias-module findings get the same silent-sub-threshold FP discipline the consumer product has, answered from documents instead of a person, no new prompt shape. Grounding claims stay single-pass unless the optional confirmation pass is explicitly scoped later. `findings[].verification.{status,method,note}` joins the schema surface; prompt registry needs an audit-mode-only route to the question generator's source_qa variant.

## §4. Business metrics layer — the sellable surface

**Decision**: every audit computes a fixed set of business-facing metrics **in code, from verdict counts** — never an LLM stating "how grounded is this?" These are the numbers the customer buys, so they get the same code-not-LLM discipline as §2.3's numeric normalization, applied one layer up.

**§4.1 Definitions** (canonical — every report and API response cites this section, never restates it). Let S, P, U, C, X = counts of `supported` / `partially_supported` / `unsupported` / `contradicted` / `unverifiable`. `Eligible = S+P+U+C` (`unverifiable` excluded from rate denominators, always reported as its own count — never hidden). **Exclusion tripwire**: excluding X from the denominator is correct (caution isn't wrongness — an unverifiable claim isn't a bad claim, it's an inconclusive check), but unchecked it's a quiet exploit — a verifier that turns timid inflates the score by shrinking `Eligible` rather than by being more accurate. If `X / (S+P+U+C+X) > 0.20`, the report must carry a prominent "low decisiveness" flag and the score is presented as annotated, not headlined.

- **Grounded rate** = `(S + 0.5·P) / Eligible` — headline. Marketing label "Groundedness Score" = `round(100 · grounded rate)`. **This definition supersedes the earlier `supported/total` computation in `audit-output-spec.md`'s worked example** — that computation predates the metrics layer existing as a design; it was a worked example's arithmetic, not a considered definition. Partial support contributes 0.5 because such claims are evidence-backed but incompletely substantiated — collapsing them to zero would tell a customer "10 of your 30 claims are ungrounded" when every one of the ten points at a real passage. **The 0.5 weight is a fixed, published grading convention, not an empirical estimate** — an explicit product decision, applied uniformly and disclosed in every report; it may be recalibrated only via ADR amendment after validation on real audits, never silently. Defensibility comes from determinism + full disclosure, not from "0.5 is correct": every report displays, alongside the headline score, the raw verdict counts, the strict fully-supported rate (`S/Eligible`, no partial credit), and `n` — e.g. "Groundedness 83/100 (strict: 67% fully supported · 20 S / 10 P / 0 U, n=30)." A skeptical buyer can recompute either number from the disclosed counts. **`audit-output-spec.md`'s worked example is updated to this formula** (see that file) so the two documents cannot diverge again.
- **Contradiction rate** = `C / Eligible` — always reported as its own headline regardless of the overall score (§4.3 rule 2).
- **Unsupported rate** = `U / Eligible`.
- **Evidence coverage** = share of claims where retrieval returned ≥1 passage above the retrieval-score floor — whether the corpus could speak to the claim at all, distinct from whether it agreed.
- **Avg evidence quality** = mean retrieval score over covered claims. Named exactly this, never "retrieval confidence" — keeps it visibly distinct from VERIFY confidence per §2.3's confidence-semantics rule.
- Every percentage displays its denominator: "75% (21/28)," never a naked percentage — small-N honesty, project-wide.

**§4.2 Score design — contradictions are not netted**: contradicted claims carry **zero** weight in the grounded-rate numerator (same as unsupported), not −1. A −1 weight would let one contradiction and 27 supported claims read as "93/100," burying the single most dangerous finding inside a reassuring composite. Instead: excluded from the numerator, and separately mandatory as a headline metric + worked example #1 (§4.3 rule 2). A contradiction is a finding, not a deduction. Score is clamped [0,100], deterministic, and reproducible from the verdict counts alone — no hidden state.

**§4.3 Presentation contract**:
1. Executive block (top of every report): Groundedness Score with denominator, the four rates as a metric strip, one plain-language sentence generated from a **template** (code-filled, not free LLM prose): "Of N checkable claims, X are supported by the supplied documents, Y lack evidence in the corpus, and Z contradict a cited source."
2. If `C > 0`: the contradiction appears in the executive block and as worked example #1, regardless of how good the score is elsewhere.
3. Drill-down table (per claim): claim text · verdict (word + icon, word primary per this project's general color-secondary convention) · confidence · evidence quote · `source_ref` with page/section — depends on §2.2's ingestion refs, which is why ref quality was scoped there. **`synthesized` is shown per claim** (not folded into the verdict weight — a synthesized `supported` is still full-weight `supported`, §4.1 doesn't change that) because claims supported only by combining passages are the known hallucination-adjacent zone; surfacing the count is cheap credibility with an eval-literate buyer who wants to see the product track its own risk areas.
4. Every worked example ends with `downstream_risk` in the customer's terms (ADR-000 §2, unchanged).
5. Single-audit JSON response gains a `scores` block: `{ grounded_rate, groundedness_score, strict_supported_rate, contradiction_rate, unsupported_rate, evidence_coverage, avg_evidence_quality, counts: {S,P,U,C,X}, eligible, low_decisiveness: boolean }`, computed at the GATE stage. This is deterministic code, so it gets unit tests against hand-computed fixtures — not a golden set (D008's `runEval`/`runDataset` pattern is for LLM-output evaluation; this has no LLM in the loop to evaluate).

**§4.4 This section forbids**: any metric produced by asking an LLM to self-rate groundedness — all metrics derive from verdict counts and retrieval logs, never model self-assessment. Combining VERIFY confidence and retrieval score into any composite (§2.3). Reporting a score without its counts, or omitting `X` (`unverifiable`) from the report. **The consumer product adopting this score** — `context-prompt-self-corpus-triage.md` (~/Downloads) already rules this out explicitly: "No composite score in the consumer view... The paid audit product keeps its rates/scores; scores are for buyers who understand them" — verified against that file, this section doesn't relitigate it, only confirms §4 stays audit-mode-only by design, not by oversight.

## §5. VERIFY reconciliation chain — code-side hardening (2026-07-29/30)

**Decision**: five deterministic reconcilers run after every VERIFY call, each correcting one narrow, named failure shape found in real production runs. None of them parse arbitrary reasoning prose as ground truth; each is scoped to a specific, testable signal.

1. **Numeric** (`reconcileNumericVerdict`) — runs `compare.ts` on any claim with an extractable number, regardless of VERIFY's raw verdict (not gated to `supported`/`contradicted`). Sets `confidence: 1` on override so `GateService`'s threshold re-gate doesn't silently undo it.
2. **Passage fallback** — when VERIFY's `evidence` is empty *or names a figure that isn't comparable*, scans the claim's own retrieved passages directly instead of trusting `note` text. Three filters, all required: (a) passages are split into **rows** (a word following a number starts a new row; a row with no content word of its own inherits the previous row's label, which is what keeps prose figures like `$(0.87) per share` attached to the "net loss" that named them), each row's label is scored against the content words preceding the claim's **own** figure, and the single best row wins — ranked by **rarity** (a word appearing in one row beats one appearing in many, counted across *all* rows including table headers) then by **label coverage** (at least half the row's label must be what the claim is about), with ties declining. This replaced bigram-adjacency matching on 2026-07-30 after the Apple probe returned `contradicted` at confidence 1 for the verbatim-true claim "Americas net sales grew 12%": in a table the row name sits immediately before its digits, so the bigram `americas net` can never form, only the generic `net sales` matched, and the claim was argued against the Total row's 17%/16%. Two follow-on bugs found while fixing it, both by the same probe: scoring rows per-passage instead of pooled let a generic Total row win when the subject's row lived in another passage; and counting word frequency only over rows *holding comparable figures* left table header rows uncounted, making "net sales" score as rare as "americas". Not the nearest-keyword picking reverted on 2026-07-29 — the subject must be named, on both sides; (b) passages whose years conflict with the claim's `period` are dropped; (c) the verdict is decided by **unanimity** across surviving figures — which one is "the" right measure doesn't matter if the claim disagrees with all of them; a split declines. Supersedes the earlier one-figure-per-passage rule, which silently skipped any passage holding two same-scale figures and was the root cause of numeric claims resolving inconsistently across ten consecutive live runs (net loss, total assets, total liabilities all went silent; EPS fired only because it was the sole scale-less figure in its passage). Pinned by the canonical four-claim gate in `numeric-reconciliation.test.ts`, which also asserts three never-fire cases so the gate can't be passed by firing on everything.
3. **Temporal** (`reconcileTemporalVerdict`) — quarter/year comparator for date-shaped claims. Scoped to `supported`/`contradicted` inputs only (unlike #1): no scale-presence-equivalent signal exists for bare dates, so it doesn't extend into `unsupported`/`unverifiable` territory.
4. **Defined-term policy** (`reconcileDefinedTermVerdict`) — a claim asserting a formally-defined term (e.g. "substantial doubt") absent verbatim from evidence is deterministically set to `partially_supported`. Curated term list, one entry per confirmed incident. Requires a negation guard and a co-occurrence anchor (e.g. "going concern") to avoid misfiring on unrelated uses of the same phrase. **Topicality gate (added 2026-07-30)**: rule 3 means "on-topic but not stated verbatim", so each term now carries a `topic` pattern and the downgrade requires at least one on-topic passage or evidence string — with nothing on-topic there is no partial support to give, and the verdict is left alone. The Apple probe granted `partially_supported` to a fabricated going-concern claim about a highly profitable company, "evidenced" by five iPhone/Mac/iPad sales narratives. Only the on-topic passages are cited.
5. **Verdict/note consistency** (`reconcileVerdictNoteConsistency`) — a `supported` verdict is invalid if its own note asserts a contradiction (regex-detected, negation-aware). **Inflections (2026-07-30)**: `\bcontradicts?\b` could never match inside "contradicted", so a note ending "Therefore, the claim is contradicted" shipped as `supported` in the Apple probe. Past tense is now accepted only in the passive (`is/was contradicted`), which asserts a contradiction, while a bare "said contradicted" merely mentions one — the distinction matters because the golden set's own case documentation uses the word descriptively. The negation regex was widened in lockstep; widening only the positive side would let negated forms through as real contradictions.
6. **Chain-reversal guard** — the five reconcilers run in sequence; each checks a shared `CODE_OVERRIDE_TAG_RE` tag first and defers to any prior stage's already-tagged decision, so a later, unrelated-dimension check can't silently undo an earlier correct one.
7. **Override note ordering** — every override note leads with the code's conclusion; the model's original note (if any) is kept but marked superseded, never left to read as the current explanation.
8. **Confidence-forcing scope**: reconcilers 1, 3 and 4 force `confidence: 1` on override; only 5 (verdict/note consistency) still passes the model's confidence through. Revised 2026-07-30 — rule 4 originally stayed behind `GateService`'s gate "as a safety net", but the gate never evaluates the heuristic, it just propagates whatever confidence the model emitted. When the model returned `0` on an evidence-empty response, `GateService` re-gated the override straight back to `unverifiable` and wiped its evidence, which is why going-concern claims kept disappearing from `eligible` between runs on identical code (visible in the run traces as a rule-3 tag sitting next to `[gated: confidence 0 below threshold 0.6]`). Rule 4 is a deterministic presence/negation check over fixed text with curated-term, negation and co-occurrence guards — its correctness does not depend on a model confidence score, so tying its survival to one was the bug, not the safeguard.
9. **Magnitude** (`reconcileMagnitudeClaim`, T041b, earlier session) — comparative-magnitude claims ("more than doubled") checked against a ratio computed from the cited evidence's own current/prior pair: ratio ≥ claimed multiple = `supported`; ≥90% = `partially_supported`; below = `contradicted`.

**Known open gap — column/period discrimination (2026-07-30, honest statement, not closed)**: the comparator resolves *which row* a figure belongs to, never *which column*. Two consequences, both reproduced live on the real Apple 10-Q probe. (a) `CURRENCY_RE` requires a literal `$`, so an all-bare table row (`Total operating expenses 18,896 15,278 37,275 30,721.`) yields zero candidates and is invisible; the claim `Provision for income taxes was $4,530` was therefore compared against the **Net income** row, the only `$`-bearing row in that passage, and landed on `contradicted` only because the values happened to differ — correct by accident, not by logic. (b) A claim quoting a real figure from the **wrong column** cannot be caught at all: `Total operating expenses were $15,278 for the quarter` (`period: fiscal Q2 2026`) is the Q2 **2025** column — Q2 2026 is `18,896` — and because `15,278` genuinely appears in the correct row, the unanimity rule splits and declines. It resolved `supported` in both live runs, with the model's own note stating the column was 2025. `claim.period` is populated on every claim and is currently **unused** by the comparator: it is passed to `compare()` on both sides, so `compare.ts`'s period check can never fire. Until the resolution below ships, the model's period reasoning is the only guard against this class, and it is not reliable.

**Also rejected, before shipping — column-legend parsing**: an attempt to close the gap by reading a `Column order throughout this section: ...` legend out of the passage. That string is a **fixture annotation** in `evaluations/golden/audit/source-filing.md`, not text from the real filing; the fix passed every test and the probe while being a guaranteed no-op on any real customer document. Recorded because the failure mode is instructive: green tests plus a green probe proved nothing, because both contained the annotation. It also caused three self-inflicted regressions (scale words splitting off their numbers, inherited row labels tying and declining, trailing claim words re-matching a ratio's denominator). Any future solution keyed on a magic phrase, or validated only against the probe payload, is not a fix.

**Planned resolution — constrained structural reconstruction (decided 2026-07-30, not yet implemented)**: table structure is recovered once at ingestion, never during VERIFY, through a pipeline that keeps every judgment in code:

```
source -> deterministic table detection -> LLM transcription (temperature 0)
       -> deterministic validation -> persist validated parse -> comparator -> deterministic verdict
```

1. **Detection is deterministic** (repeated numeric rows, multiple values per row, nearby period tokens) and gates LLM invocation to detected candidates only. It also produces the authoritative **column count** — the LLM is never asked how many columns there are, only checked against a number code already computed.
2. **The LLM transcribes structure only** — `{row, values: [{period, value}]}`, with period labels returned **verbatim from the header including duration** (`Three Months Ended March 28, 2026`). It never sees the claim and never judges.
3. **Validation is all-of, scoped to the same table block**: every value verbatim in the block; the row label in the block (not merely elsewhere in the passage); period/header tokens in the block; value count equal to the detected column count; no value assigned to two periods; and the **parsed period sequence must match the left-to-right order of the header's period tokens**. That last check is the one that matters — value-order reconstruction alone passes a transposed parse, since swapping which period owns which column leaves the value sequence untouched while every value and label stays verbatim.
4. **Failure discards the structured interpretation** and falls back to the existing row-scoped, period-blind comparator — which may miss a contradiction but **must not invent one**. It never falls through to unscoped candidate matching.
5. **Period matching stays in code**: the parser returns verbatim header labels, and deterministic code maps `claim.period` to the satisfying column. Year alone is insufficient — `fiscal Q2 2026` must select the three-month `18,896`, not the six-month `37,275`, which is a different measurement period and must never participate in the primary contradiction decision (it may appear as supplementary context only).
6. **The parse is persisted, keyed by `corpus_id`**, not cached in memory, so the same corpus reuses the same interpretation across audits and re-runs — otherwise two runs of one input could disagree, which is the single promise this layer exists to protect. Recorded in `llm_calls` with the usual model/prompt-revision stamping, `temperature: 0`.

**Input constraint (found 2026-07-30, applies regardless of implementation)**: column/period discrimination is only possible when the passage supplied to the pipeline **retains its column/header information**. Headerless tabular text must fall back, never infer missing column identity. This is not a tunable: in `source-filing.md` the `income-statement` and `eps-table` excerpts contain **zero** period tokens once the fixture annotation is removed, so no approach — LLM or deterministic — can recover which column a figure sits in. Those two blocks are therefore pinned as *negative* coverage (a headerless block must be ineligible and must not produce a false contradiction), and the positive column-discrimination acceptance moved to the `segment-table` block, which carries a genuine header. The fixture is deliberately **not** repaired by reconstructing a header we cannot verify against the filing — inventing source data to make a test pass is the contamination this whole section exists to prevent. Worth stating to customers before an engagement rather than discovering it during one.

**Acceptance (revised 2026-07-30, segment table)**: `Europe net sales were $24,454 million for the quarter` (`period: fiscal Q2 2026`) resolves `contradicted` with evidence `28,055` — the Q2 2026 column — and `24,454` must never be presented as the contradicting figure. The parse must use the segment table's real header, and the case must hold with the fixture annotation removed.

**Boundary (the line this design rests on)**: *structural reconstruction* — which cell a number occupies — is a transcription task and may use an LLM under validation. *Arithmetic judgment* — whether one number matches another, and what verdict follows — stays exclusively in code (D018 §2.3). The two must never be merged into one call.

**§5.10 — VERIFY response reliability (2026-07-31)**: a VERIFY response that survives `repairWithFallback` but still fails `VerifyResponseSchema` used to throw, which `AuditService` turned into a failed audit. Measured live at roughly **1 run in 5** on the Apple probe, recovered only by a human relaunching — unacceptable for a self-serve paste-your-document flow. Now the batch is retried up to `VERIFY_SCHEMA_ATTEMPTS` (3) times, and if it is still unparseable the batch's claims are set to `unverifiable` with a note naming the parse failure, so the audit completes with a visible gap instead of a hard error. Injection-suspected responses remain a hard stop and are never retried (§2.3) — which is why the shared `withRetry` helper, which retries everything except rate limits, is deliberately not used here.

**Known declined case — consecutive percent columns (2026-07-31)**: in `columnsForCells`, a percent ("Change") cell inherits the first USD column of its run; when two percent cells are adjacent with no USD cell between them, the second has no run to anchor to and currently falls back to `headerDates[0]` with a null duration, fabricating a column identity instead of declining. Trigger condition: a table row whose cells are ordered `… USD, %, % …`. Not reachable in the Apple products/segment tables (every percent follows a USD pair) and usually blocked first by the row-width check against `detectTableCandidate().columnCount`, but it is the same shape of bug as the row-scoping and period-scoping defects before it — a fallback that guesses rather than returns null. Tracked here rather than left as tribal knowledge; the fix is to return null when `runStart === -1`.

**§5.11 — period narrows, never selects (2026-07-31)**: the column fix originally used `claim.period` to *select* one cell. `claim.period` is a free-text field EXTRACT **infers** (`"Q3 2025"`, `"first six months of Q3 2025"`), and on a stress run against the Apple Q2 2026 filing EXTRACT tagged **all 46 claims `"Q3 2025"`** — including the claim that quotes the cover page's own "quarterly period ended March 28, 2026". The comparator then faithfully selected the prior-year column and contradicted **nine verbatim-true income-statement claims** at confidence 1, identically across three runs, while the two genuinely wrong-column claims matched that column and came back `supported`. The verdict logic was correct throughout; its input was not. Root cause is architectural, not a parsing bug: an unvalidated, inferred LLM field had been made load-bearing for a deterministic override — the exact failure class this section exists to prevent — and the acceptance tests hid it by hand-writing the correct period. **§5.12 — period can only decide supported vs. unsupported, never contradicted (2026-07-31)**: after three rounds of hardening `narrowByPeriod`'s text parsing (comparative-aside stripping, multi-year decline, footnote-marker guards) each round closed one failure and a fresh one kept appearing in the same shape — a year at the end of a sentence (`"...in 2025."`) was still invisible to the lookahead-bounded year regex, reproducing the original false-accusation bug through different punctuation. The parsing was never going to be exhaustively correct. The actual fix is architectural: **`contradicted` no longer depends on period matching at all.** A figure is `contradicted` only when it appears nowhere in the metric's own row/context, under any period — plain unanimity, identical for a table row or a prose sentence, no column or period logic involved. A figure that IS in the row but not in the claimed period's column is `unsupported` (the source states it, for another period) rather than `contradicted`. This makes a wrong period-regex a lost catch, never a false accusation, by construction — no amount of remaining regex imperfection can turn "different period" into "the numbers disagree." `narrowByPeriod` (§5.11) still exists and still narrows for the `supported` case, but its mistakes now land in the safe direction. Table/prose distinction is no longer load-bearing for the safety property, only for precision.

Two changes: (a) period **filters** a row's candidates rather than selecting one — but note the honest limit, found on review: narrowing to exactly one candidate *is* selection, since unanimity over a single element is trivially unanimous. The guarantee therefore only holds while the surviving set is unambiguous, which is enforced explicitly: text from the first comparative marker onward (`versus`, `compared with`, `up from`, `a year earlier`, ...) describes the baseline rather than the figure's own period and is excluded, and when the claim names more than one year no year narrowing happens at all, leaving every candidate for unanimity. Without those two rules a bare year in a comparative aside retargeted the column and contradicted verbatim-true figures — `"Gross margin was $54,781 million, versus 2025 levels."` was returned `contradicted` against the 2025 column, and it was phrase-dependent (`"up from 2025"` survived, `"from the 2025 figure"` did not), so the failure was unpredictable as well as wrong; (b) period signals are read from `claim.claimText` and the table's own columns (unstated year = the table's most recent column, i.e. the current period), never from `claim.period`. Also fixed alongside: a bare accounting-negative cell `(52)` parsed as `+52`, its prose form "negative $52 million" on the claim side, and a leading footnote marker `(1)` being read as a `-1` cell (which shifted every column by one) — told apart from a real accounting negative by the row's own shape, since markers are 1-2 bare digits beside comma-formatted figures. `selectColumnForPeriod` was deleted rather than left exported: it encoded the `claim.period` dependency this section removes, and dead-but-green tests around it would have read as sanctioned API. Pinned by the WRONG-PERIOD GATE in `numeric-reconciliation.test.ts`, where every claim deliberately carries the wrong inferred period.

**§5.10 addendum — provider timeouts (2026-07-31)**: the same stress run failed **2 of 5** with `[GoogleGenerativeAI Error] ... This operation was aborted` — a provider timeout at VERIFY, not a schema failure, so the §5.10 retry (which wraps only the parse) did not cover it. `env.AI_TIMEOUT_MS` defaults to 10s, sized for the story flow; an audit batch carries a whole claim batch plus its retrieved passages. EXTRACT and VERIFY now pass an explicit 60s `timeoutMs`. Retrying the *call* itself, and revisiting `BATCH_MAX` for large audits, remain open.

**Rejected**: a sixth VERIFY prompt revision to fix evidence-population reliability directly — six-plus prior revisions have each fixed one shape while regressing another (going-concern alone flipped seven times across runs); betting on prompt-following reliability for a new shape inherits that track record instead of removing the dependency.

**Also rejected, reverted after shipping**: a keyword-proximity fallback that searched retrieved passages by nearby words when evidence was empty. On real dense filing text it matched a claim to a same-keyword, wrong-measure figure (e.g. a liabilities claim matched to unrelated GAAP opex guidance) — a confident, wrong accusation. Proximity can only establish "these words are close," never "same measure." The passage fallback in #2 above replaces it with typed numeric extraction only, no proximity.
