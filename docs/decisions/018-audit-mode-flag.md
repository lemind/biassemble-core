# D018 — B2B Audit Mode: Service Boundary, Flow, and Verification

One ADR, four parts: where audit mode lives (§1), what it does end to end (§2), how bias findings get false-positive-checked (§3), and the business-facing metrics computed from the results (§4). Kept together because they're one coherent decision — how the audit product is built inside this repo — not four independently revisable choices.

---

## §1. Mode flag, not a separate service

**Decision**: The B2B audit product (ADR-000, top-level docs/) is built as `mode: "story" | "audit"` inside this repo — one deploy, one Postgres instance, new `audit` pg schema alongside the existing `core` schema. Not a new repo, not a fork.

Router picks prompt file + orchestrator by `mode`, same pattern as the existing question/assessment split in `orchestrators/`. EXTRACT and VERIFY (§2) are two new prompt files registered through the existing prompt registry — reusing the repair pipeline (D004), evidence-binding discipline (D002), and eval harness (`runEval`/`runDataset`, D008) as-is, applied to claims instead of biases. `/audit` runs go through Inngest (new *usage* of the job infra already proven by `src/jobs/eval-run.ts`, not new infra) since audits are batch, not sync — the latency-sensitivity work behind the sync reflection endpoints doesn't apply here.

**Mode-branching invariant**: `mode` branching is permitted **only** at the orchestration layer (routes → orchestrators → prompt selection). All lower layers — retrieval, repair pipeline, LLM providers, telemetry, storage abstractions, parsers, evaluators — stay mode-agnostic. An `if (mode === "audit")` anywhere below orchestration is an architecture violation, not a style preference: it's how "mode is a load-bearing conditional" (Consequences, below) stays contained to one layer instead of leaking through the codebase.

**Why**: Audit mode needs almost everything this repo already has — prompt registry, Zod contracts, repair pipeline, `llm_calls` observability, CI eval gate, Bearer auth, esbuild→Vercel deploy. It differs only in persona (neutral verification vs. reflective), input shape (claim triple vs. story), and sync-vs-batch — none of which require a second deploy target. A separate service would duplicate all of the above for a solo dev who can't carry two deploy targets in parallel (ADR-000 §4: "parallel tracks ship nothing"). A permanent fork risks the consumer flow drifting out from under the eval discipline that's the actual product moat (ADR-000 §1).

**Do not**: Stand up a second repo/service for audit mode. Let the consumer flow (story/questions/assessment) change to accommodate audit mode — b2b-change-plan.md §0 requires it untouched. Put customer corpus data in the `core` schema — it goes in the separate `audit` schema (§2.4) so it can be dropped post-engagement without touching consumer tables.

**Consequences**: every existing investment pays off immediately for EXTRACT/VERIFY with no reimplementation; `mode` becomes a load-bearing conditional through routes → orchestrators → prompts (acceptable at current scope — revisit only if a second person/team takes ownership of one product, or audit-mode load genuinely conflicts with consumer-mode resources on the same deploy; neither holds today); corpus retrieval stays in biassemble-engine, extending its existing boundary (`POST /corpus`, per-claim `/retrieve`) rather than a third service — this section governs core-side placement only, not the core/engine split, which ADR-000 already implies.

## §2. The audit flow: pipeline, corpus, documents, verdicts, data lifecycle

**Decision (pipeline)**: unit of work is the **claim**, not the story:

```
EXTRACT (1 call: output_text → atomic checkable claims)
  → RETRIEVE (per claim: candidate passages from THIS ENGAGEMENT's corpus — taxonomy retrieval untouched)
  → VERIFY (claim + passages → verdict + verbatim quote, batched 5–10 claims/call sharing passages)
  → GATE (confidence threshold; aggregate rates; clean flag; sub-threshold logged not surfaced)
  → BIAS MODULE (optional, off by default, secondary layer, source_qa-verified per §3)
```

The pipeline is **append-only**: each stage consumes the immutable output of the previous stage and never rewrites upstream artifacts — EXTRACT output is frozen before RETRIEVE runs, retrieved passages are frozen before VERIFY runs, verdicts are frozen before GATE runs. Claims are batched 5–10 per VERIFY call solely for token efficiency; verdicts are logically independent per claim — no claim's verdict may be influenced by another claim sharing its batch. A shared-batch dependency (e.g. a prompt that reasons "given claim 3 was contradicted, claim 4 is probably also suspect") is a defect, not a feature.

`POST /audit` accepts `{ mode: "audit", domain, task, output_text, sources[], options }`, returns the single-audit JSON (`audit_id`, `claims[]`, `rates`, `gated_candidates[]`, `bias_flags[]`, `meta`).

**Identity, idempotency, versioning**: every claim gets a `claim_id` at EXTRACT, immutable through RETRIEVE → VERIFY → GATE → review UI → label dataset; every passage gets an immutable `passage_id` at corpus ingestion, and VERIFY output references `passage_ids`, never chunk indices or array position — matching between stages by array order is forbidden, since a re-sort or a dropped chunk silently corrupts the mapping. `audit_id` is immutable; re-running the same input creates a new audit with a new `audit_id` (inputs hashed via `input_ref` so re-runs are linkable to each other); review-page overrides attach to the audit as separate records and never rewrite pipeline output — this is what makes the override-label moat dataset (§2.4) trustworthy provenance instead of edited history. `meta` records, per audit: `prompt_revision` (extract and verify stamped separately), `model_revision` (exact model string per stage), `embedding_model` + dimension, `corpus_version`, `taxonomy_version` (when the bias module ran), `threshold`, and pipeline code version — every knob stamped, same discipline §2.1 already applies to `corpus_version` alone, extended to all of them, because evaluations are only comparable when every knob that could have changed is on the record.

**Schema reconciliation (found on review, resolved here)**: the two source docs disagree on top-level shape. `audit-output-spec.md` nests claim verdicts inside `grounding.claims[]` alongside a separate `findings[]` for bias results. `context-prompt-b2b-transformation.md` §6 flattens this to `claims[]` + `bias_flags[]`. **`context-prompt-b2b-transformation.md`'s flat shape is authoritative** — it's what this section and the endpoint above already describe, and it keeps claims and bias findings as siblings rather than nesting one inside the other, which matches §3's rule that they're verified through different mechanisms (VERIFY vs. source_qa). `audit-output-spec.md`'s nested `grounding{}`/`findings[]` shape is superseded; do not implement it.

**§2.1 Corpus + embedding (product ADR-002)**: engine gains `POST /corpus { corpus_id, documents[] }` and `POST /retrieve { corpus_id, query, top_k }`. `corpus_id` scopes every row; one corpus per engagement, never shared across customers. MiniLM's 256-token limit is inadequate for 10-K-length passages — swap via the existing `EmbeddingProvider` interface (no new abstraction), exact model choice is an implementation task, not decided here; the contract is that it must be swappable the same way MiniLM was. **No migration exists because nothing existing changes**: corpus tables are new tables (`bias_embeddings`'s pattern is `embedding vector(384) NOT NULL` — dimension fixed by the column type, per the existing schema, not a per-row field), created at the new model's dimension; the taxonomy path stays on MiniLM/384 untouched; `embedding_model` is already recorded per row today (`db/queries.py`'s insert includes it) and the same column carries over to corpus tables. `corpus_version` stamped in every audit response, same discipline as `taxonomy_version`. Retrieval-score logged per claim, unconditionally — this is what lets "unsupported" mean "sources are silent" instead of "retrieval failed," same lesson as `kb_entries_retrieved`.

**§2.2 Document ingestion, v1 scope**: sources are PDFs and EDGAR HTML/XBRL, not clean text (silently assumed away in earlier drafts). V1 scopes to **EDGAR HTML only** — what the Fintool run (ADR-000 §4 step 6) needs, and it's structured markup, not scanned-PDF OCR. Output: clean text + page/section references, since `source_refs` quality in VERIFY output depends on it. PDF parsing deferred until a target past Fintool requires it — do not build it speculatively.

**§2.3 Verdict taxonomy — canonical, defined once, here**:
- `supported` — a passage states this; quote verbatim; 2+ passages combined sets `synthesized: true`.
- `partially_supported` — passage covers part of the claim, or is more general than the claim (source more specific and fully covering = `supported`).
- `unsupported` — no provided passage addresses the claim. Asserts absence from retrieved passages only, never "this is false."
- `contradicted` — a passage directly opposes the claim for the **same subject, measure, period, and scope (segment/geo/consolidated)** — strict comparability required. A different number possibly referring to a different period/measure/scope is `unsupported` with a note, never `contradicted`.
- `unverifiable` — confidence below `{{threshold}}`; verdict goes to trace only, never guessed into the report.

**Confidence semantics**: `confidence` originates exclusively from VERIFY's own output. Retrieval score is **not** confidence — it's evidence quality (how good the retrieved passage match was), logged separately per claim per §2.1's retrieval-score-logging rule. The two are never multiplied, averaged, or otherwise folded into one number; gate thresholds (the `{{threshold}}` above) apply to VERIFY confidence only, never to retrieval score.

**Arithmetic happens in code, never in the LLM.** A deterministic normalization step runs between EXTRACT and VERIFY: units, scale, currency, and periods get parsed to canonical form, and derived values (growth rates, ratios, sums, pp-vs-% conversions) get computed in code from quoted source values. VERIFY's job is to *compare* already-canonical numbers, never to compute them — an implementer putting derivation arithmetic inside the VERIFY prompt is the exact failure this normalization step exists to prevent. Numeric rules VERIFY still applies post-normalization: unit/scale must match (€m vs €k mismatch = `contradicted` only if same measure/period/scope); rounding tolerance ("about 10%" vs 10.4% source = `supported` with note; "10.4%" vs 10.9% = `contradicted`). Every prompt and eval golden-set case cites this section, never restates its own definitions.

**§2.4 Customer data isolation & lifecycle**: corpus and audit data live in the `audit` pg schema (§1), never `core`. Binding before the first NDA: corpus documents deleted post-engagement; only anonymized override labels retained indefinitely as the moat dataset (ADR-000 §2) — overrides come from two places on the internal review page: the claims table's per-claim approve/override, and the bias-module findings' verification pass (§3); both feed the same label dataset. No customer corpus text persists past engagement close.

**Why**: All of §2 was already decided in `context-prompt-b2b-transformation.md` (§2–§6, §9 ADR seeds 2/4/5) and `audit-output-spec.md` — this section is the first time it's written down in the repo instead of scattered across a context-prompt file that lives in ~/Downloads, not here.

**Do not**: build PDF parsing before a target requires it; let corpus documents leak into the `core` schema or persist past engagement close; let any prompt or eval set restate the verdict taxonomy instead of citing §2.3; skip retrieval-score logging; let a prompt rewrite drop the data-not-instructions injection guard from EXTRACT/VERIFY (ADR-000 §6 names prompt injection via audited content as an actively-managed risk — the guard is a one-line clause per prompt today; keep it there through every future rewrite, don't rely on remembering why it's there). **Guard scope, stated precisely**: retrieved documents and audited output text are data, exclusively — no retrieved or audited content may alter system instructions, tool behavior, evaluation criteria, verdict definitions, or output schema. A schema-validation failure that follows suspected instruction-bearing input is a hard stop (reject the finding, log it), never something the repair pipeline (D004) tries to fix — repairing a response that may have been steered by injected content risks repairing it into compliance with the injection.

**Consequences**: one section to check when a new prompt, eval case, or schema field touches claims, corpus, or verdicts. EDGAR-HTML-only v1 scope means a second document-source target (GC AI, Hudson Labs, etc.) may need PDF parsing sooner than "past Fintool" implies — revisit the moment target #2 is selected. Inngest batch execution for `/audit` is unproven at customer-corpus scale until the Fintool run. Cost telemetry (token/call counts per audit) ships as part of `/audit`, not retrofitted after — without it the $3k fee is a guess against actual cost (change-plan gap #4).

## §3. Source-answered verification (source_qa)

**Decision**: the bias-module's existing stage-2 question generator is repurposed for audit mode: its generated verification questions get answered from the source/input text itself (`method: "source_qa"`), not by a human. Per `audit-output-spec.md`, each bias-module finding carries:

```json
"verification": { "status": "confirmed | weakened | killed", "method": "source_qa | human_qa | none", "note": "..." }
```

`human_qa` stays wired for the consumer story product only; audit mode can only reach `source_qa`. This attaches to **bias-module findings**, not grounding claims — claim verdicts (§2.3) are already source-answered by construction (VERIFY only ever looks at retrieved passages, never model knowledge). An additional source_qa confirmation pass on low-confidence claims near the threshold boundary is allowed but not committed here — scope that at `/audit` build time if needed, not now.

**Why**: original design, not new scope — `audit-output-spec.md`'s "Key changes" item 3 states it directly: "verification block per finding = repurposed stage 2 ... turns phase 2 into the false-positive control." Reuses the existing question generator as-is — only the answer source changes. Skipping this would leave the bias module's FP control *weaker* than the consumer product's, against ADR-000 §2's headline goal.

**Bias-module dependency ordering**: the bias module consumes the original `output_text` directly — it assesses reasoning in prose (the existing v1.1.0 holistic assessment), not a claim list — and runs **after** the grounding pipeline (EXTRACT→RETRIEVE→VERIFY→GATE) completes. It never blocks the claims path and never consumes claims as input; no `extract → bias → verify` wiring exists or should exist. This matters because it's tempting to assume the bias module could reuse EXTRACT's claim list to save a pass — it can't, because reasoning flags (framing, cherry-picking, overconfidence) live in the prose structure of `output_text`, not in the atomic facts EXTRACT pulls out of it.

**Do not**: make `human_qa` reachable from audit mode (§1 already forbids a human mid-run; `source_qa` is machine-only, no contradiction). Attach a `verification` block to grounding claims by default — VERIFY already is that check for claims. Surface a finding whose `verification.status` is `"killed"` — killed candidates are `gated_candidates`, logged, never shown. Feed the bias module a claims list instead of `output_text`, or run it before GATE — ordering and input shape above are both load-bearing, not incidental.

**Consequences**: bias-module findings get the same silent-sub-threshold FP discipline the consumer product has, answered from documents instead of a person, no new prompt shape. Grounding claims stay single-pass unless the optional confirmation pass is explicitly scoped later. `findings[].verification.{status,method,note}` joins the schema surface; prompt registry needs an audit-mode-only route to the question generator's source_qa variant.

## §4. Business metrics layer — the sellable surface

**Decision**: every audit computes a fixed set of business-facing metrics **in code, from verdict counts** — never an LLM stating "how grounded is this?" These are the numbers the customer buys, so they get the same code-not-LLM discipline as §2.3's numeric normalization, applied one layer up.

**§4.1 Definitions** (canonical — every report and API response cites this section, never restates it). Let S, P, U, C, X = counts of `supported` / `partially_supported` / `unsupported` / `contradicted` / `unverifiable`. `Eligible = S+P+U+C` (`unverifiable` excluded from rate denominators, always reported as its own count — never hidden). **Exclusion tripwire**: excluding X from the denominator is correct (caution isn't wrongness — an unverifiable claim isn't a bad claim, it's an inconclusive check), but unchecked it's a quiet exploit — a verifier that turns timid inflates the score by shrinking `Eligible` rather than by being more accurate. If `X / (S+P+U+C+X) > 0.20`, the report must carry a prominent "low decisiveness" flag and the score is presented as annotated, not headlined.

- **Grounded rate** = `(S + 0.5·P) / Eligible` — headline. Marketing label "Groundedness Score" = `round(100 · grounded rate)`. **This definition supersedes the earlier `supported/total` computation in `audit-output-spec.md`'s worked example** — that computation predates the metrics layer existing as a design; it was a worked example's arithmetic, not a considered definition. Partial support contributes 0.5 because such claims are evidence-backed but incompletely substantiated — collapsing them to zero would tell a customer "10 of your 30 claims are ungrounded" when every one of the ten points at a real passage. **The 0.5 weight is a fixed, published grading convention, not an empirical estimate** — an explicit product decision, applied uniformly and disclosed in every report; it may be recalibrated only via ADR amendment after validation on real audits, never silently. Defensibility comes from determinism + full disclosure, not from "0.5 is correct": every report displays, alongside the headline score, the raw verdict counts, the strict fully-supported rate (`S/Eligible`, no partial credit), and `n` — e.g. "Groundedness 83/100 (strict: 67% fully supported · 20 S / 10 P / 0 U, n=30)." A skeptical buyer can recompute either number from the disclosed counts. **`audit-output-spec.md`'s worked example is updated to this formula** (see that file) so the two documents cannot diverge again.
- **Contradiction rate** = `C / Eligible` — always reported as its own headline regardless of the overall score (§4.3 rule 2).
- **Unsupported rate** = `U / Eligible`.
- **Evidence coverage** = share of claims where retrieval returned ≥1 passage above the retrieval-score floor — whether the corpus could speak to the claim at all, distinct from whether it agreed.
- **Avg evidence quality** = mean retrieval score over covered claims. Named exactly this, never "retrieval confidence" — keeps it visibly distinct from VERIFY confidence per §2.3's confidence-semantics rule.
- Every percentage displays its denominator: "75% (21/28)," never a naked percentage — small-N honesty, project-wide.

**§4.2 Score design — contradictions are not netted**: contradicted claims carry **zero** weight in the grounded-rate numerator (same as unsupported), not −1. A −1 weight would let one contradiction and 27 supported claims read as "93/100," burying the single most dangerous finding inside a reassuring composite. Instead: excluded from the numerator, and separately mandatory as a headline metric + worked example #1 (§4.3 rule 2). A contradiction is a finding, not a deduction. Score is clamped [0,100], deterministic, and reproducible from the verdict counts alone — no hidden state.

**§4.3 Presentation contract**:
1. Executive block (top of every report): Groundedness Score with denominator, the four rates as a metric strip, one plain-language sentence generated from a **template** (code-filled, not free LLM prose): "Of N checkable claims, X are supported by the supplied documents, Y lack evidence in the corpus, and Z contradict a cited source."
2. If `C > 0`: the contradiction appears in the executive block and as worked example #1, regardless of how good the score is elsewhere.
3. Drill-down table (per claim): claim text · verdict (word + icon, word primary per this project's general color-secondary convention) · confidence · evidence quote · `source_ref` with page/section — depends on §2.2's ingestion refs, which is why ref quality was scoped there. **`synthesized` is shown per claim** (not folded into the verdict weight — a synthesized `supported` is still full-weight `supported`, §4.1 doesn't change that) because claims supported only by combining passages are the known hallucination-adjacent zone; surfacing the count is cheap credibility with an eval-literate buyer who wants to see the product track its own risk areas.
4. Every worked example ends with `downstream_risk` in the customer's terms (ADR-000 §2, unchanged).
5. Single-audit JSON response gains a `scores` block: `{ grounded_rate, groundedness_score, strict_supported_rate, contradiction_rate, unsupported_rate, evidence_coverage, avg_evidence_quality, counts: {S,P,U,C,X}, eligible, low_decisiveness: boolean }`, computed at the GATE stage. This is deterministic code, so it gets unit tests against hand-computed fixtures — not a golden set (D008's `runEval`/`runDataset` pattern is for LLM-output evaluation; this has no LLM in the loop to evaluate).

**§4.4 This section forbids**: any metric produced by asking an LLM to self-rate groundedness — all metrics derive from verdict counts and retrieval logs, never model self-assessment. Combining VERIFY confidence and retrieval score into any composite (§2.3). Reporting a score without its counts, or omitting `X` (`unverifiable`) from the report. **The consumer product adopting this score** — `context-prompt-self-corpus-triage.md` (~/Downloads) already rules this out explicitly: "No composite score in the consumer view... The paid audit product keeps its rates/scores; scores are for buyers who understand them" — verified against that file, this section doesn't relitigate it, only confirms §4 stays audit-mode-only by design, not by oversight.
