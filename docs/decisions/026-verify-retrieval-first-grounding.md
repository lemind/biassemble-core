# D026 — VERIFY Retrieval-First Reordering (Grounding Recall)

## §1. Trigger

A real live-eval failure (g05-statue-of-liberty, 2026-08-10, run `c858ef85-...`) recurred despite v2.1.0 (2026-08-07) already adding an explicit "verbatim-only, never from memory" instruction to the EVIDENCE section for exactly this failure class. Confirmed via `grounnel_gate_events`/`grounnel_llm_calls` telemetry, not guessed: VERIFY's raw output was `verdict: "contradicted"`, `confidence: 1`, `reason: "The passage states the Statue of Liberty was a gift from France, not Canada."` — factually correct — but `evidence` was Wikipedia's well-known opening sentence about the statue, not text from whichever of the three fetched pages (NPS.gov, Wikipedia, a French-culture blog) the model actually received in that call. Gate #1 (`applyContradictionEvidenceGate`) correctly caught this on both the original pass and D025's reconciliation retry (`gate: contradiction_evidence, reason: evidence_not_grounded`, both passes) and safely degraded to `unsupported` — **zero false accusations**, per the eval's own report. The system worked as designed; the model still occasionally answers famous facts from parametric memory instead of the given passage.

## §2. Why this isn't a regression, isn't a gate problem, and isn't a temperature problem

- Not caused by anything in T036 (Gemini schema enforcement, injection-guard fix, or the unrelated TEMPORAL SCOPE addition in v2.2.0) — confirmed by reading the actual gate events; none of those code paths are on this claim's route.
- Not a gate gap: the deterministic substring-grounding check already exists and already fired correctly, twice. This is a **recall** problem (a true claim occasionally goes unconfirmed), not a **precision** problem (nothing false gets asserted) — the prompt's own `CORE PRINCIPLE` ("false positives are worse than false negatives") means this is the intentional, acceptable failure direction, not proof the system is broken.
- Not fixable by a new gate — this is "did the model actually read the given passage or answer from memory," a judgment call, not a fixed pattern (AGENTS.md #12, already applied twice this session to the injection-guard and D025 gate #5).
- Not a temperature issue — VERIFY already runs at `temperature: 0`. This is a parametric-knowledge bias (well-known facts have a stronger memorized association competing with the in-context instruction, counterintuitively making FAMOUS facts *more* susceptible to this than obscure ones), not a sampling-randomness problem.

## §3. Decision — two small, targeted prompt-only changes (v2.3.0)

**Reorder STEP 1** from "identify the passage fact" to explicitly require locating and confirming the exact quote *before* reasoning about the relationship — retrieval-first, not reason-then-justify. Small edit to the existing STEP 1-3 procedure, not a rewrite; matches this file's own established pattern (v2.0.0's decision-table restructuring measurably helped, v2.1.0's additional declarative "never from memory" line only partially did).

**Add a one-line reminder immediately before `CLAIM_PASSAGE_PAIRS:`** — the existing verbatim-only instruction sits mid-prompt, distant from where the actual passages appear in context. A short reminder right at the point of use is a recency nudge, near-zero cost, plausible upside.

## §4. Explicitly out of scope

- `BEGIN/END PASSAGE` banner delimiters — considered, rejected. That pattern targets a single free-text passage block; this pipeline's payload is already JSON (`"passage": "..."`), a harder machine boundary than ASCII banners would add. Not worth a payload-shape change for likely-lower marginal benefit here.
- A model-side self-check pass ("is my quote really in the passage?") — considered, rejected. Strictly weaker than the existing deterministic substring check + retry (which always fires; a self-check is itself just another model output the model could skip or get wrong).
- Any temperature/generation-parameter change — already at 0; doesn't address a bias.
- A new gate, a second retry layer, or any code change — this stays prompt-only.
- Building dashboards/metrics on first-pass-vs-retry grounding recovery rate now — the query is cheap (`grounnel_gate_events` already has everything needed) but not worth building until this recurs at a rate that actually matters. Noted for later, not now.

## §5. Addendum (2026-08-10) — the temporal-scope lesson didn't reach the deterministic numeric gate

v2.2.0 (this same file's own history) taught VERIFY's own reasoning that a narrower-period snapshot doesn't contradict a broader-period threshold claim. It never touched `applyNumericGate` (gate #2, `gates.ts`) — pure code, no LLM involved, which independently compares a claim's number against whatever number appears in `evidence` and forces `supported`/`contradicted` for threshold language ("surpassed", "exceeded") with zero period awareness.

Real recurrence, g11, confirmed via `grounnel_gate_events`: VERIFY's raw verdict was `partially_supported`; gate #2 saw claim "$3.5T" vs. evidence "$3.2T (July 2025)" and forced `contradicted` via pure numeric comparison, oblivious to the mismatched period. A reconciliation retry fired for an *unrelated* reason (gate #5 flagged the original answer), and the retry's evidence happened to come back `null` — gate #2's own `if (!evidence) return no-op` guard is what actually prevented a false accusation, not anything that understood the period mismatch. Had the retry's evidence been non-null, gate #2 would have forced `contradicted` again, and — capped at one retry — that would have shipped as a real false accusation. This was luck, not a fix.

**Decision:** add one new guard to `applyNumericGate` — before any threshold/equality override (either direction), extract years from `claimText` and `evidence` (a pattern with the same intent as the B2B audit reconciler's `passagePeriodConflicts`, not imported from it — see reviewed findings below). If the claim names a year and evidence names ANY year the claim doesn't — even if a matching year ALSO appears elsewhere in the evidence — the gate abstains, no override either direction. Deliberately coarser than a strict "zero overlap" rule: the real g11 evidence string spanned 2022-2025 across different, unrelated figures, and a matching year happened to also be present for an unrelated reason, so "some overlap exists somewhere" isn't a safe enough test. Two prompt-consultation sync passes independently converged on this shape (comparability as a precondition for *any* override) and both explicitly rejected a new retry path — deterministic-logic bug, not a case for asking the model again.

**Explicitly not doing:** narrowing gate #2 to equality-only claims (would remove real, working capability for the common same-period case); an asymmetric-only-toward-"supported" override rule as a separate mechanism (redundant once the comparability guard exists); any new gate in the chain (gate count stays 5) or new retry layer.

**Known, accepted cost of the coarse rule** (found by code review, 2026-08-10): an incidental, unrelated year in evidence — a filing citation, a publication date, a regulatory-effective-date mention — can make the gate abstain even when a genuinely matching year is *also* present and the comparison would have been safe. Accepted, not fixed: this failure direction is a missed catch (false negative), not a false accusation, consistent with `CORE PRINCIPLE`. A precise fix would require associating a number with its *own* nearby year (not just year-token-set overlap across the whole string) — tried during code review and found fragile (naive sentence-splitting breaks on abbreviations like "Inc."; a fixed character window is either too narrow or catches the wrong adjacent sentence, verified against the real evidence string). Revisit only if this recurs at a rate that matters.

**Code review findings (medium effort, 2026-08-10, all fixed except one deliberately not fixed):** (1) `YEAR_RE`'s original lookahead `(?![\d.])` excluded a year followed by ANY period — including an ordinary sentence-ending one — silently no-op'ing the entire guard for the most common claim phrasing ("...surpassed $X in 2024."); confirmed independently by 2 review passes via direct execution. Fixed: `(?!\d)(?!\.\d)` excludes only a genuine decimal, not a sentence end. (2) The lookbehind didn't exclude a preceding `$`, so a dollar figure in the 1900-2099 range (e.g. "$1998") could be misread as a year; fixed with `(?<![\d.$])`. (3) One new unit test ("guard doesn't over-trigger") passed for the wrong reason — its claim text hit bug (1), so it exercised the "claim has no year" early-exit, not the "years genuinely match" comparison it claimed to test; now correctly exercised now that (1) is fixed, plus two new dedicated regression tests added for (1) and (2) directly. (4) `yearsConflict` had an unreachable-in-practice null-guard; simplified to a `Set`-based two-liner. (5) `YEAR_RE` duplicates (doesn't import) the B2B reconciler's inline pattern — noted, deliberately not fixed: `passagePeriodConflicts`'s regex isn't exported, and exporting it plus changing a second feature's file was judged out of scope for this review pass.

## §6. Addendum (2026-08-10) — root causes upstream of VERIFY itself: candidate selection and a memory anchor

§1-5 all treat VERIFY's own reasoning/gates as the fix surface. Two-pass review of the g05/g11 recurrences (a self-review plus an independent "sync" pass, both converging) concluded the two most consequential remaining gaps are upstream of VERIFY entirely:

**g11 (search recall):** confirmed via `grounnel_search_calls` that T031's Tavily fallback did request and receive all 16 results, each already fetched with full text in the one API call (`include_raw_content: true` — no extra network cost). But `resolveEvidence`/`hybrid-provider.ts`'s `runFallback` never ranked those 16 by relevance to the specific claim — it sorted only by fetch `status` ("ok" first) and sliced to `MAX_CANDIDATES` (3), then `resolveEvidence` took the first "ok" one unconditionally, even when a later, already-fetched candidate both passed gate #4's relevance filter and the first one didn't. The Apple-$3.5T case's selected passage never contained the claimed figure; nothing downstream — including gate #4, which only ever sees the one already-chosen candidate — got a chance to prefer a better one from the 13 that were fetched and discarded.

**g05 (memorized-page substitution):** the byte-identical fabricated quote surviving an explicit reconciliation retry (§1) indicates prompt wording alone won't close this class — the model isn't uncertain, it's confidently substituting its own trained recollection of a *recognized* page for the in-context text. `pairs[].source_url` (`pipeline.service.ts`'s `callVerify`) is serialized directly into `claim_passage_pairs` and reaches the model, even though nothing in the prompt asks the model to use it — it exists purely as a leftover convenience field, never read back from the model's response. For a page the model recognizes (Wikipedia's Statue of Liberty article, confirmed as one of the 3 actually-fetched sources), the URL is a direct memory-activation cue that costs nothing to remove.

**Decision:** four changes, ordered cheapest/highest-confidence first:
1. **Rank Tavily-fallback candidates by relevance before selecting** (`hybrid-provider.ts`), not just by fetch status. Reuses gate #4's own key-term extraction (`extractKeyTerms`, moved to `src/lib/claim-terms.ts` as the shared home so both the `providers/` and `orchestrators/` layers can import it without inverting dependency direction) as the scorer — no new model call, no new API spend, all 16 candidates already have text in hand.
2. **Stop sending `source_url` to VERIFY.** Drop the field from `callVerify`'s serialized `pairs` entirely — it was never read back from the model's response, so removing it is a pure subtraction, not a behavior change to anything except the memory-activation cue.
3. **`resolveEvidence` tries the next-best already-fetched "ok" source when the first fails gate #4's relevance check**, instead of giving up the moment the single first "ok" source fails. Combined with (1)'s ranking and a raised fallback-retention cap (`MAX_CANDIDATES` → a separate, larger constant for the already-fetched Tavily pool only — no new fetches, so no new cost), this is the "bounded escalation" both review passes recommended, implemented as reuse of an already-fetched pool rather than a new retry/wave loop.
4. **VERIFY prompt v2.4.0** — a further STEP 1 reinforcement (name the exact passage sentence before writing evidence), same low-confidence "small nudge" category as v2.1.0/v2.3.0's prior wording changes. Not the offset/character-index mechanical-extraction idea raised in review — that needs a schema change (new start/end fields, gate #1 updated to prefer them) and is deliberately deferred, not folded into this addendum, until (1)-(3) are validated against a live-eval re-run and shown to leave a residual worth that scope.

**Explicitly not doing here:** true offset-based mechanical quote extraction (schema change, deferred per above); fuzzy-match repair of a fabricated-but-similar quote (deferred behind seeing whether (2) alone shrinks the residual, per the same reviews' own sequencing logic); multi-passage evidence (T032, already tracked, unrelated scope); a new `insufficient search coverage` verdict state (deferred until (1)+(3) exist and can actually distinguish "not in the 16" from "was in the 16, never looked").

## §7. Addendum (2026-08-10) — the structural fix: cite a sentence number, not generated text (T043/T044)

§6's fixes shipped (candidate ranking, `source_url` removed) and were re-verified via two production curl runs where g05 and g11 both landed correctly. A subsequent real live-eval run (`27f346db-...`) recurred anyway: `grounnel_llm_calls` showed the model producing the exact same fabricated "gift... from the people of France... Bartholdi... Gustave Eiffel" sentence on BOTH the original VERIFY call and D025's reconciliation retry — byte-identical, confidence going UP (0.9 → 1.0) on the retry rather than down. This is decisive evidence that removing the URL (§6) closed one trigger (page-identity recognition) but not the other: the model recognizes an extremely famous claim ("Statue of Liberty... gift...") from the CLAIM TEXT ALONE, with no page identity needed, and a firmer reworded retry prompt does not change a confidently "known" answer — it isn't uncertain, so there's nothing for a "try harder" instruction to grab onto.

**Decision:** stop iterating on prompt wording for this failure class (v2.1.0 through v2.4.0 all did, with diminishing/zero returns) and make fabrication structurally impossible instead. New `src/orchestrators/grounnel/passage-sentences.ts` splits each resolved passage into sentences in code and selects/numbers a claim-relevant, capped subset (`buildPassageSentences`, reusing gate #4's own `extractKeyTerms`/`scoreKeyTermMatches` as the relevance scorer — same infrastructure as §6's candidate ranking, applied one layer deeper). VERIFY's prompt and output schema change: the model cites `evidence_sentence_ids` (an array of sentence numbers) instead of generating `evidence` as free text. `pipeline.service.ts`'s `callVerify` resolves those numbers back to real, code-extracted sentence text (`resolveEvidenceFromSentenceIds`) before anything else in the pipeline sees the result — any id that doesn't resolve (out of range, invented) nulls out the WHOLE answer, not a partial match. Downstream of that resolution point (gates, persistence, tests), nothing changes: `VerifyResultSchema`'s `evidence: string | null` shape is unchanged, gate #1 still runs as a backstop (now defending against a malformed/out-of-range index rather than typed fabrication, since typed fabrication is no longer representable in the schema), gate #2 still extracts numeric facts from the resolved text.

**T044, bundled into the same version bump:** added a `MEMORIZED-FACT TRAP` section to the prompt — a worked negative example using the actual g05 Statue of Liberty case (wrong: citing a real-but-irrelevant sentence number from memory-driven confidence; correct: `unsupported`/`null` when no given sentence states it). This is a concrete worked example, not another emphatic rewording, so it isn't subject to the "we already tried firmer wording and got a byte-identical repeat" argument that closed off further pure-wording iteration.

**Side benefit, not the primary goal:** the injection-guard's `quotedFields: ["evidence"]` exclusion (T036) is now structurally unnecessary for VERIFY's raw response — the model can no longer reproduce arbitrary scraped web text in its output at all (only integers), so the "scraped 'you are now subscribed' text quoted back by the model" false-positive class this fixed is now impossible through this path, not just excluded. Left the exclusion mechanism itself in place (harmless, and `verify.service.ts`'s separate B2B audit path still needs it).

**Explicitly not doing:** true character-offset citation (considered in review, rejected — models are unreliable at exact character counting even when not fabricating, layering a new arithmetic failure mode on top; sentence-level integers avoid this by construction); removing gate #1 (kept as a backstop, cost is trivial); fixing the model's sentence-*relevance* judgment (it can still cite a real-but-wrong sentence — a different, non-safety-critical failure mode, unchanged by this fix and not in scope).

## §8. Addendum (2026-08-10) — two unrelated failure classes, upstream of everything in §1-§7 (T045/T046)

T043/T044 (§7) shipped and were confirmed working — 2 production curl runs found the correct g05/g11 answers with genuine, non-fabricated evidence. The golden-set eval still failed across 4 runs, but on two DIFFERENT claim shapes than anything §1-§7 addressed: g08-napoleon-birthplace (VERIFY's response silently missing one claim entirely) and a further g11-bloomberg-fallback recurrence (the correct page inconsistently present in Tavily's own result set — 2 of 5 recent attempts at the identical claim found it, 3 didn't). Two independent review passes converged on ranking three candidate fixes; the top two are built here, the third deliberately deferred.

**T045 — response completion.** VERIFY's batch contract is `N ids in -> N results out`; the code previously treated this as a probabilistic property (degrade whatever's missing at the end) rather than an invariant to enforce. Real case: a 17,580-token batch (moderate, not the earlier 77K-token case that first surfaced this — so not purely a "context too large" effect) answered one Napoleon claim correctly and had no entry at all for an adjacent one in the same batch. Fix: diff requested vs. answered claim ids, unconditionally, after every batch; fire one small fill-in `callVerify` call for exactly the gap (never the whole batch again); give the fill-in claim(s) identical downstream treatment (gates, T034 retry, D025 classifier) to a normally-answered one. Only degrade what's still missing after that one attempt.

**T046 — deterministic search query.** The query sent to search providers was the claim's raw declarative sentence, unmodified. Search indexes are keyword-optimized, not sentence-optimized — "Apple's market capitalization surpassed $3.5 trillion in 2024." carries filler words ("was", "in", "the") a search engine gets no signal from. Fix: `buildSearchQuery()` extracts entities+numbers (reusing the same classification `extractKeyTerms` already uses for relevance scoring, refactored into one shared `tokenize()` so the two can't drift), preserves original case/order (unlike `extractKeyTerms`, which lowercases and Set-orders for case-insensitive matching — wrong properties for a readable query), falls back to the raw claim text when nothing key-worthy is found.

**Reviewed finding, same day:** the first version wired `buildSearchQuery` into `resolveEvidence`, one layer too high — that query reaches both `HybridSearchProvider`'s DIY discovery (which embeds it in `Use the google_search tool to search the web and check this claim: "${query}"` for Gemini's own grounding search) and the Tavily fallback. A keyword fragment in the DIY prompt degrades Gemini's own reasoning on the *primary* path every claim hits first, not the narrow Tavily-only surface T039's ranking was correctly scoped to. Fixed same day: `resolveEvidence` reverted to the full claim text; `buildSearchQuery` moved one layer deeper, applied only where `hybrid-provider.ts`'s `runFallback` calls the real Tavily API — `query` itself stays the full claim sentence everywhere else (Gemini's prompt, ranking, telemetry).

**Explicitly deferred, not built — a third idea, ranked lowest by both reviews:** splitting one claim into multiple search queries to widen retrieval coverage. Rejected as a *default*: two naive rephrasings of the same claim tend to return near-duplicate results (same index, same top pages), and unconditionally doubling search cost before proving the single deterministic query is insufficient is premature. Both reviews independently suggested this only makes sense as *adaptive escalation* — fire a second, differently-angled query only when the first attempt's ranked candidates don't confirm the claim (reusing the same "unmatched numeric anchor" trigger concept named back in D026 §6, never built) — not as an always-on multiplier. Not tracked as a task yet; revisit only once T045/T046's effect is measured and a real residual remains.

## §9. Addendum (2026-08-10) — a production crash T039 exposed, unrelated to grounding (T047)

A golden-set run on g10-fabricated-silence (a deliberately nonsense claim — "The Zorgonian Institute's 1932 expedition...", testing that VERIFY correctly reports silence for a topic nothing real exists about) failed with a Zod `invalid_format`/"Invalid URL" error on `sources[1..7].url`, `run: null` — the eval harness couldn't even parse a claim result. Reproduced directly (not eval-only): a live `/status/:id` call for the same claim returned a 500, same error. Root cause found via `grounnel_claims.sources`, not guessed: two of eight retained Tavily results had `url: "/goto?url=CAESWwHuR6pN..."` — a relative Google redirect/tracking artifact Tavily's API occasionally returns instead of a real absolute URL, not something this session's code produced. `tavily-provider.ts` passed `r.url` through unvalidated; when the response was later serialized against `ClaimSource.url`'s `.url()` format check, it 500'd the entire request — not just marked one source unusable.

This bug predates T039 — `tavily-provider.ts` never validated `r.url` — but T039 raising `FALLBACK_RETAINED_CANDIDATES` from 3 to 8 (§6) measurably raised the odds of a malformed-URL result surviving into the retained/persisted set, especially for exactly this claim shape: a fabricated topic where Tavily can't find real matches and is more likely to return low-quality/redirect-artifact results in the first place.

**Decision:** filter out any Tavily result whose `url` isn't a real absolute `http`/`https` URL, before it ever becomes a candidate — same precedent `hybrid-provider.ts`'s DIY discovery already applies via `parseSafeUrl` (filters malformed/unsafe URLs before they're ever fetched or returned), just without the private-host/SSRF check DIY needs and Tavily doesn't (we never fetch `r.url` ourselves — Tavily already supplied the content). A relative redirect link isn't a real, fetchable, citable source anyway, so dropping it entirely (not just downgrading its status) is correct — it was never going to be a meaningful "attempted source" to show anyone.

**Explicitly not done:** touching `ClaimSource.url`'s schema to relax the format check (would let genuinely broken citations reach end users — the schema is right, the input feeding it was wrong); any change to `hybrid-provider.ts`'s DIY path (not implicated — its own `parseSafeUrl` filter already covers this class for DIY candidates, only Tavily's raw pass-through was missing it).

## §10. Addendum (2026-08-10) — the same T039 fix, extended to the path it was never applied to (T048)

Live-test recurrence: the identical claim ("Napoleon Bonaparte was five feet two inches tall.") landed `supported` on one run and `unsupported` on another. Confirmed via `grounnel_search_calls`, not guessed: both runs fetched the exact same 2 real DIY candidates (`ripleys.com/stories/tall-napoleon-bonaparte`, `en.wikipedia.org/wiki/Napoleon_complex`) — only their order differed, because Gemini's live discovery search returns candidates in a non-deterministic order call to call, and `resolveEvidence` took the first "ok" one unconditionally. This is exactly the problem T039 (§6) already solved — for the Tavily *fallback* path only. DIY discovery, the path every claim hits first, was never given the same treatment.

**Decision:** extract the scoring/sort logic T039 added inline to `runFallback` into one shared `rankByRelevance(query, results)`, used by both the DIY branch and `runFallback`. Same comparator, same behavior, one implementation instead of two that could drift apart — a second review pass of the original T039-extension proposal specifically flagged this as the right shape (provider owns "fetch, rank, return" as one contract, not two paths with different semantics). No new fetches, no new cost: `MAX_CANDIDATES` (what actually gets fetched) is unchanged, only the order of the already-fetched results.

**Considered and not done:** an additive/weighted score (entity match + numeric match + year match, weighted separately) instead of the existing flat "count of matched key-terms." `extractKeyTerms` already blends entity and numeric tokens into one term set, so a candidate matching both already scores higher than one matching only one — the same practical effect the weighting proposal wanted, without a second scoring dimension to maintain. Kept the existing scorer as-is, consistent with this file's own repeated precedent (D026 §6, §8) of preferring the simplest mechanism that closes the observed gap over a more elaborate one with no demonstrated need yet.

## §11. Addendum (2026-08-10) — multi-passage evidence, Phase 1 (T049)

VERIFY only ever saw ONE retrieved passage per claim, no matter how many real pages were fetched — tracked since D024 as T032 ("the largest, riskiest task in this phase"), never built. Requested directly, with an original proposal bundling three changes at once: multi-passage pooling, adaptive 3-tier escalation (3→5→8 passages), and auto-triggering a second/Tavily search call whenever VERIFY returned `unsupported`. Two independent consultation reviews of that proposal converged on the same correction: don't ship all three together — too many simultaneous variables to know which one is responsible for any observed change in recall. Ship the foundational capability (pool a small, fixed number of passages) alone first, measure it against the golden set, then decide whether escalation earns its added complexity and cost.

**Decision (Phase 1 only):** `resolveEvidence` now pools up to `MAX_VERIFY_PASSAGES` (3) ranked, relevant sources per claim instead of picking the single best one (T048's ranking still decides *which* 3). Each pooled passage is numbered independently and grouped under a source label — "A" = highest-ranked, "B", "C" — rather than merged into one flat renumbered sentence list. This directly closes a gap a review pass flagged in an earlier draft of this plan: a single shared numbering scheme (`1, 2, 3, 4, 5...`) lets two sentences from *different, possibly disagreeing* documents read as adjacent context from one continuous document. The model now cites `{source, n}` pairs (`evidenceCitations`), and — because each citation resolves against its own cited source's sentence list specifically, not a pooled/flat one — a citation can never land on the wrong document's text, by construction, regardless of what it says it's citing.

The prompt (`verify/system.json`, v4.0.0) gained a `MULTIPLE SOURCES` section stating explicitly that sources are ranked and may be complementary (a claim established by combining two sources) or may disagree — a real question a review pass raised that had no answer in a single-passage world: "source A says X, source B says Y — what is VERIFY supposed to do?" Also added a new worked CONSISTENCY EXAMPLE demonstrating a legal joint-source citation, and a telemetry log line in `callVerify` recording passage/sentence counts per call, so a future "did this help?" measurement isn't guessing whether pooling actually happened.

**Explicitly deferred, not built:** adaptive escalation (3→5→8, or a token-budget version) and auto-triggering extra search on an `unsupported` verdict — both require Phase 1's effect to be measured first; building them now would make it impossible to attribute any recall change to a single cause. Per-citation grounding checks (verify a citation's resolved text against only its claimed source rather than the joined-passage blob gate #1 uses) — raised in review as a roadmap item, then found to already be moot: `resolveEvidenceFromCitations`'s per-source resolution already guarantees this by construction, independent of what gate #1's backstop separately checks.

**Reviewed finding, same day, fixed:** the first version of `resolveEvidenceFromCitations` indexed a plain JS object by the model-returned `source` string with no ownership check — a citation naming `"constructor"` or `"__proto__"` would resolve to an inherited `Object.prototype` value instead of `undefined` and throw on the next `.find()` call, which (unlike a normal unresolvable citation, designed to null out just one claim's evidence) would take down the entire batch in `runBatch`'s primary/fill-in paths. Fixed with a `hasOwnProperty` guard; regression test covers the 5 most common prototype property names.

No DB/schema change. Full suite 942/943 (1 pre-existing unrelated `it.todo`), clean typecheck, after fixing a real prototype-pollution-shaped bug found in review.

## §12. Addendum (2026-08-10) — cross-claim contamination in a batched VERIFY call

**Trigger:** A fresh, non-golden-set live test (a 16-claim, multi-domain story, not shaped like any prior golden-set entry — Antikythera mechanism, Marie Curie, Camp David Accords, blue whale, Coinbase, etc.) surfaced a new failure class. Traced via `grounnel_llm_calls`' raw `parsed_output` for the batch: an 8-claim VERIFY call answered the claim "Marie Curie won Nobel Prizes in chemistry and physics" — id `eb2ecaf0-...` — with `verdict: "contradicted"`, `reason: "Sentence A5 explicitly states the Camp David Accords were signed on 17 September 1978."` The SAME batch's actual Camp David claim (id `b6ba2836-...`) got nearly identical reasoning. `evidenceCitations` for the Curie claim still resolved to real, grounded text — her own pooled passage's sentence 5 (a garbled but real Wikipedia infobox blob) — because each claim's citations resolve against that claim's OWN independently-pooled passages (D026 §11). So gate #1 (verbatim-evidence-grounding) passed it clean: the evidence really was real, the model just paired it with a completely different claim's reasoning and verdict. `grounnel_gate_events` confirmed this was the PRIMARY call, not a retry — none of the 5 existing gates catch it, because none check whether `reason` is topically about the claim it's attached to, only whether `reason` is self-consistent with `verdict` (D025 §2) or whether `evidence` is real (gate #1).

**Decision — gate #1b, `applyClaimReasonOverlapGate` (`gates.ts`), deterministic, reuses D026 §6's `extractKeyTerms`/`scoreKeyTermMatches`:** for a `contradicted` verdict, extract the claim's own key terms (entities + numbers, same classification already used for search-query building and passage relevance ranking) and check whether `reason` contains at least one of them. Zero overlap → downgrade to `unsupported`, evidence nulled, same convention as every other downgrade-only gate here. Fail-open when the claim has no extractable key terms (nothing to check) — same convention as every other consumer of `extractKeyTerms`. Chain position: immediately after gate #1 (`contradiction_evidence`), before gate #2 (`numeric`) — deliberately AFTER gate #1 so it never has to re-derive grounding, and BEFORE gate #2 so a numeric-driven flip to `contradicted` (which doesn't go through a reason-quality check anywhere else) isn't second-guessed by a reason field that's often generic/boilerplate for that path. Also raises an `ERROR` diagnostic, so it goes through the same T034/D025 §2 one-shot reconciliation retry as gate #1's own downgrade — which structurally can't repeat this failure, since a single-claim retry call has nothing else in its request to cross-wire with.

**Validated against real data before writing, not guessed:** an early draft checked claim-key-term overlap against a simplified, hand-written reason string and found a false-positive risk (a legitimate answer paraphrasing "the Emu War" as "the campaign"). Re-tested against the ACTUAL reason text VERIFY produces in production (pulled from a real live run) — real reasons consistently restate the claim's own entities even while quoting passage text, so the false positive didn't reproduce against real data. Kept the check; the lesson was to validate against real model output, not a hand-simplified proxy for it.

**Considered and rejected:** a vector/embedding similarity check between `claim` and `reason` instead of lexical key-term overlap — would catch subtler contamination (reasoning that shares one proper noun but is still off-topic), which hasn't been observed yet, at the cost of a new embedding API call per `contradicted` claim, a similarity threshold to tune empirically, and new infrastructure. Deferred until a real case surfaces that the lexical check misses — same "ship the narrow fix for the observed failure, extend only if measured" pattern this file's own §10/§11 already followed. Asking the model to self-check its own answer in the same call — already established as unreliable (D025 §1: this is literally the failure mode the whole gate-chain/classifier design exists to route around).
