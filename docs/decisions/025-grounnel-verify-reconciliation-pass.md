# D025 — Grounnel VERIFY Reconciliation Pass

## §1. Trigger

A second real g04 (`World War II ended in 1943`) failure, distinct from the one T034 fixed (2026-08-07). This time VERIFY's raw output was `verdict: "unsupported"`, `evidence: ""` — not `"contradicted"` with hallucinated evidence — so T034's `needsRetry` trigger (only fires when `verdictBeforeGate1 === "contradicted"`) never activated. Confirmed via `grounnel_gate_events` for run `2e755218-...`: all 4 existing gates ran, none overrode anything (`overridden: false` on every row). The model's own `reason` field proved it had read the correct end date ("...September 1, 1939 – September 2, 1945, but does not state that it ended in 1943") — it extracted the contradicting fact but never reflected that in `verdict`/`evidence`. None of the 4 existing gates catch this: `reason_consistency` only matches explicit contradiction wording (`CONTRADICTION_LANGUAGE_RE`); `implicit_negation` only matches a literal ", not Y" pattern; `contradiction_evidence` only runs when verdict is already `"contradicted"`; `numeric` short-circuits on empty `evidence` and never reads `reason`.

## §2. Decision

**A 5th gate — `counterfact_ignored` — general, LLM-classifier-driven, not regex-based:** the initial design (extract a numeric/date fact from `claimText` and `reason` via `extractNumericFact`, compare) turned out to not even cover g04's own case — `extractNumericFact` (`verify-reconcilers.ts`) only recognizes currency (`$...`) or percent (`...%`) patterns, never bare years/dates, and was deliberately not widened (it's the shared, hardened B2B/D018 function; Grounnel-only scope creep on it is out of bounds). More fundamentally, claims aren't only numbers — regex-per-fact-type doesn't generalize to names, places, or qualitative facts either. Replaced with a small batched LLM classifier: for every claim in a VERIFY batch whose primary verdict isn't already `"contradicted"`, one additional batched call asks *"does this reasoning support this verdict?"* against `{claim, reason, verdict}` — a `NO` becomes the `counterfact_ignored` diagnostic. This needs its own new, minimal, versioned prompt asset (unlike the reconciliation retry below, which reuses `grounnel-verify` unchanged) — classification is a different task from verification.

**Where this runs — `runBatch`, not inside `runGateChain`:** `runGateChain` stays the existing pure, synchronous function (5 gates' worth of string/regex logic, still fully unit-testable with no I/O). The classifier is a new async step in `runBatch`, batched the same way `callVerify` already batches claim/passage pairs — one call per VERIFY batch, not one call per claim. Its per-claim `consistent: boolean` result is passed into `runGateChain` as a plain input value; `runGateChain` itself never makes an LLM call. Real cost: this roughly doubles the primary pass's LLM-call count (one classifier call added to every batch, in addition to the primary VERIFY call) — inherent to a general judgment-based check, not avoidable while keeping it general.

**Chain position — the `counterfact_ignored` check point sits between `implicit_negation` and `contradiction_evidence`:** `reason_consistency → implicit_negation → [counterfact_ignored, using the classifier result] → contradiction_evidence → numeric`. By the time it's evaluated, a claim that's going to become `"contradicted"` via language-based detection already has — `counterfact_ignored` only applies to the remainder (still not `"contradicted"`, but the classifier said the reasoning doesn't support the verdict). This ordering is what makes §3's mutual-exclusivity claim hold: `contradiction_evidence` only runs on verdicts that are (already, or freshly) `"contradicted"`, `counterfact_ignored` only runs on verdicts that aren't — a claim can trigger at most one of the two per pass.

**Diagnostics, not a single retry-reason string:** `runGateChain` collects every gate's finding into `diagnostics: Array<{ code: string; severity: "ERROR" | "WARNING" | "INFO"; details: string }>` instead of one `needsRetry` boolean tied to one gate. T034's existing case (`evidence_null`/`evidence_not_grounded` from gate #1) and this new `counterfact_ignored` case both become diagnostic entries. Retry fires when any diagnostic is `severity: "ERROR"` — today that's both existing cases; `WARNING`/`INFO` exist in the type now so future gates can log without forcing a retry, but nothing currently emits them. `severity` is a code-level/runtime field only — not a new DB column; `grounnel_gate_events.reason` (already persisted) still records which gate fired and why, sufficient telemetry while every real diagnostic is `ERROR`. Reviewed finding: gate #5's `overridden` is always `false` (it never changes verdict, only flags) unlike gates #1-4, where `reason` is only ever non-null when `overridden` is `true` — querying gate #5's activity needs `WHERE gate = 'counterfact_ignored' AND reason IS NOT NULL`, not the `overridden = true` filter the existing `grounnel_gate_events_overridden_idx` index is built for.

**One reconciliation prompt, not one prompt per diagnostic code:** the existing `grounnel-verify` system prompt (v2.1.0) is unchanged — no new prompt file, no new prompt version. Only the `user` message (already a plain hardcoded string in `callVerify`, not registry-tracked) becomes dynamic on retry: shows the claim, the full previous answer (`verdict`, `evidence`, `reason`), and the diagnostics list, then instructs the model to treat the passage as the sole source of truth and produce a corrected answer resolving every listed diagnostic — explicitly instructed to replace its previous answer entirely rather than anchor on it unless that answer remains consistent with the passage, and explicitly required to quote only text that appears in the passage if returning `"contradicted"`. No vague language ("try again", "think carefully") — the instruction is deterministic repair, not a second guess.

**Everything else reuses T034 unchanged:** capped at exactly one reconciliation attempt (no recursion), gate chain re-runs on the retry's output (already enforces grounded quoting via gate #1), `callType` stays `"consistency_retry"` (not renamed — already shipped, telemetry is already clean via diagnostics + existing `reason` codes), hard failures (no evidence found, JSON parse errors) remain on their existing separate paths untouched.

## §3. Why generalize now instead of adding a second retry path

A second, gate-#5-specific retry (a `retryReason` string with an if/else prompt branch) was the initial proposal and was rejected during design: every future gate would otherwise need its own prompt file or its own branch, and the two failure modes found in this codebase so far (evidence-not-grounded, counterfact-ignored) already show that pattern doesn't scale past 2. The diagnostics-array shape costs nothing extra today (only one diagnostic will ever be present per claim under current gates, since gate #1 and gate #5's trigger conditions are mutually exclusive) and removes the need to touch this design again when a 6th gate is added later — it only needs to append to `diagnostics`.

## §4. Explicitly out of scope

- `severity` as a persisted DB column — deferred until a real `WARNING`/`INFO`-only diagnostic exists; premature to migrate for a field with one value in practice.
- Renaming `callType: "consistency_retry"` — already shipped, diagnostics already make the "why" legible without a rename.
- Any change to D024's search-escalation scope (T029-T033) — this ADR is VERIFY-side only, same boundary T034 already established.

## Consequences

- `runGateChain`'s signature changes (new `reasonVerdictConsistent: boolean | null` input) and its return shape changes (`needsRetry: boolean` → `diagnostics: Diagnostic[]`); `runBatch`'s branch on it needs updating, plus T034's existing 3 tests need to read the new shape (still asserting the same behavior).
- One new gate + tests (`gates.ts`, `gates.test.ts`), still pure/sync/no I/O.
- A new async batched classifier step in `runBatch`, with its own new prompt asset and version (`grounnel-consistency-check` or similar) — the one genuinely new prompt this ADR introduces; the reconciliation retry itself still reuses `grounnel-verify` unchanged.
- Real, ongoing cost increase: roughly doubles the primary VERIFY pass's LLM-call count (one classifier call per batch, in addition to the primary VERIFY call), on top of the reconciliation retry's existing per-flagged-claim cost.
- `callVerify`/`retryVerifyClaim`'s retry-call `user` string becomes dynamic — needs the previous answer and diagnostics threaded through, a small signature change.
- No schema migration.
